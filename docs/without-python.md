# Python なしで使える範囲と、考え方

bg-skills は「ボードゲームを、エージェントが不足なく読めるゲームの定義（YAML）に書き、その定義で遊び・確かめ・改訂する」ための道具です。
`bg` コマンド（Python）は、その定義を機械で確かめ、局面を作り、見え方を伏せ、多数局を回すための道具です。
**定義そのものと考え方は Python に依存しません。** この文書は、Python を入れずに使える範囲と、入れると何が増えるかをまとめます。

> 補足：`bg` を使うのに Python の知識は要りません。[uv](https://docs.astral.sh/uv/) を 1 つ入れれば、Python 本体と依存は uv が用意します。
> 「Python を入れられない・入れたくない」場面（会社の端末、ブラウザだけの Claude、紙の上の設計）を想定した文書です。

## 考え方（道具がなくても通じるもの）

| 考え方 | 中身 | どこに書いてあるか |
|---|---|---|
| ルールの文が正本 | ルールは自然文（`rules`）が正本。機械の層（条件・手順・終わり）は、作品が選んで書いた分だけ。食い違えば文が正しい | 定義の `rules`、CTR-F-001 |
| 詳細ルールと手引き | 審判用の細かい文は `detail: true`。遊ぶ人の手引きには出さないが、定義と裁きでは使う。強さは 詳細ルール＞手引き＞裁定＞機械の層 | CTR-F-001「詳細ルール」 |
| 裁定 | 文で決まらない点（ルールの穴）は、問い・裁定・理由・重み（official＞author＞designer＞keeper）で `rulings` に書く。決まらなければ `status: open` で問いだけ残す | 定義の `rulings` |
| 部品と置き場 | 定義に出るものは、置き場（エリア）と部品（オブジェクト）の派生で書く。山札・手札・盤のマス・得点の道も置き場 | CTR-F-001「派生の一覧」 |
| 見え方 | 置き場ごとに「誰に、何が（ある・枚数・表・順）見えるか」を書く。手札は持ち主だけ、山札は誰にも、など | 定義の `visibility` |
| 局面は記録から作る | 局面は保存せず、操作の記録（1 行 1 操作）を初めから行い直して作る。取り消しも、定義を直した後の追従も、この形なら素直 | CTR-F-002 |
| 用語と表記 | 呼び名は遊びの一部。用語（`terms`）に、使う言葉・使わない言葉（`avoid`）・初出の表記（`first`。例：巡（ラウンド））を書く | 定義の `terms` |
| 案で試す | 本体の定義を写さず、変えるところだけを書いた断片（案）を重ねて試す。同じ id の要素は差し替え、新しい id は足し、`remove` で消す | CTR-F-007 |
| 試した記録を残す | どの版・どの案で・何局・どうだったかを残し、改訂の理由にする | CTR-F-007「試行の記録」 |

## できること・できないこと

| 作業 | Python なし | Python（`bg`）あり |
|---|---|---|
| 定義を書く・読む | **できる**。形式は `docs/bg-def.schema.json`（JSON Schema）と CTR-F-001。YAML の拡張を入れたエディタ（VS Code の YAML 拡張など）なら、項目名の打ち間違いをその場で知らせる | `bg check`：参照先・式・形式・用語の表記まで確かめる |
| 手本を読む | **できる**。`examples/`（三目並べ・オセロ・チェス・将棋・麻雀・人狼・架空のカードゲームなど） | 同じ |
| アイデアを定義に起こす（スキル bg-design） | **ほぼできる**。手順のうち、聞き取り・部品と置き場・ルールの文・用語・裁定は文書の作業。コマンドの手順（check・fuzz）は飛ばし、目で確かめる | すべて |
| ルールと定義の突き合わせ（bg-rules-audit） | **ほぼできる**。文と定義を読み比べ、穴を裁定にする。数え上げ（文だけのルール・一度も行えない行為）は手で | `bg complexity`・`bg fuzz` が数える |
| 用語と表記の点検 | **できる**（目で探す）。用語の一覧を見ながら、使わない言葉を検索する | `bg check` の `wording` が場所と言い換えを出す |
| 遊ぶ人の手引きを作る | **手で書ける**。定義の `rules`（`detail` でないもの）・部品・用語・決まった裁定を並べればよい | `bg rulebook` が定義から書き出す（初出の表記も） |
| エージェント（や人）がキーパーになって試し遊び | **できるが弱い**。キーパーが定義を読み、局面を手で書き、操作を記録の形（1 行 1 操作）で残す。隠れた情報は、席ごとに別の会話・別の人に見せる分を手で分けて守る | `bg show --as P1` が席ごとの見え方を作り、記録も伏せる。厳格モードで外れた行為を断る |
| 多数局の自動の対局・案の比べ | できない | `bg selfplay`・`bg compare`（席ごとの勝ちの割合・長さ・決着しない割合）と試行の記録 |
| 卓の画面・Tabletop Simulator への書き出し | できない（画面はサーバーから局面を受け取る） | `bg serve`・`bg tts` |

## Python なしで回すときの勧め

1. **定義を先に書く。** 道具が無くても、定義（YAML）は後から `bg` でそのまま確かめられます。書き方は Python の有無で変わりません。
2. **記録の形を守る。** 試し遊びの操作を `{"op": "move", "obj": "c3", "to": "hand-P1", "by": "P1", "rule": "R2"}` のような 1 行ずつで残しておけば、後で `bg` を入れたときに、そのまま局面を作り直せます（CTR-F-002）。
3. **隠れた情報は、見せる人ごとに分ける。** Python なしでは機械が伏せてくれません。キーパー役と席の役を別の会話（別の人）にし、席の役には、その席から見える分だけを渡します。
4. **決まらないことは裁定に。** 迷った点は推測で埋めず、`rulings` に `status: open` で問いとして残します。
5. **数で決めることは後回しに。** 先手の有利・長さ・決着しない穴は、多数局を回さないと分かりません。ここだけは `bg`（uv）を入れる価値があります。

## スキルとの関係

`skills/` のスキルは `bg` コマンドを使う前提で書いてありますが、手順の多く（聞き取り・ルールの文・用語・裁定・報告の形）は文書の作業です。
Python なしの環境では、コマンドの手順を「目で確かめる」に読み替えて使えます。プラグインとしての配布は、まだしていません（このリポジトリを clone して `claude --plugin-dir <フォルダ>` で試せます）。
