# RUL-004：カタンの仕上げ、惨劇RoopeR の完全な再現、アーキテクチャ設計の進め方について

## Exchanges

| # | 話者 | 内容 |
|---|---|---|
| 1 | 利用者 | （/goal）指示したことが完了し、アーティファクトで報告するまで継続。5h枠がぎりぎりになったらタイマーかけて再開して |
| 2 | 利用者 | カタンが終わったらレビューして、要求要件の整理、 |
| 3 | 利用者 | その後惨劇るーぱーの完全再現ためしてみて、また遊んでみて、要求要件の整理 |
| 4 | 利用者 | それが終わったらアーキテクチャ設計に移ってよい |
| 5 | 利用者 | アーキテクチャ設計でも概念の定義を重視して設計して。okfspecsつかって |

## Results

| 発言 | 行き先 | 結果 |
|---|---|---|
| #1 | 開発ルール | 人の確認をはさまず、完了してアーティファクトで報告するまで続ける。使用量の枠が近づいたら status.md に状況を書き、タイマー（CronCreate）で再開する |
| #2 | 開発ルール | カタンを仕上げる（再現できないもの G1〜G10 のうち、カタンに要るものを汎用の概念として入れる）→ エージェントのレビュー → 要求・要件の整理。「カタンが終わったら」を、G1〜G3 を入れて再現を仕上げることと解した（推定。根拠：直前の報告で G1〜G3 を入れるかを尋ねていた） |
| #3 | 開発ルール | 惨劇RoopeR を完全に再現する（local/。公開しない。根拠は sangeki の資料）→ エージェントに遊ばせる → 要求・要件の整理 |
| #4 | 開発ルール | その後、アーキテクチャ設計（構造・契約・開発オブジェクト）に進む |
| #5 | 設計への指定 | アーキテクチャ設計は okf-specs の構造・契約の手順で行い、概念の定義を中心に据える（概念＝定義の形式の契約）。対象：PRD-001 r1。反映：CTR-F-001 r1 |
