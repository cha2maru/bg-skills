# 第二版：自作のボードゲームを作る人の使い方（RUL-028）

## 想定する人

自作のボードゲームを作っている人（ゲーム設計者。ひとり、または小さな仲間）。Claude Code は使えるが、bg-skills の中身は知らない。
ルールはまだ固まっておらず、遊びながら・回しながら変えていく。数値（手札の枚数・得点）だけでなく、ルールの形そのもの（手番の流れ、終わり方）も変わる。

## 導入から利用までの流れ（ユースケース）

| # | 場面 | すること | v1 で足りたか | v2 で足すもの |
|---|---|---|---|---|
| U1 | 入れる | `/plugin marketplace add`・`/plugin install bg-skills@bg-skills`。uv があるか確かめる | README だけ | スキル bg-start（入ったかの確かめ、uv の案内） |
| U2 | 始める | 自分のプロジェクトに、ゲームの作業場（定義・案・試行の記録・設計の日誌）を作る | なし（examples を写すしかない） | `bg init`（作業場の雛形。最初から bg check が通る） |
| U3 | 書きかけで回す | アイデアを定義にする。決まっていない点は open_questions・未決の裁定（status: open）に残し、決まった所だけ機械の層にする | bg-design・bg check・bg fuzz | bg-start から bg-design へつなぐ |
| U4 | 状態を知る | 何が決まっていないか、機械の層がどこまでか、最近の結果はどうだったかを見る | complexity・rulings に散らばる | `bg status`（設計の状態の一覧） |
| U5 | 案を試す | 定義を写さずに、数値やルールの違う案を重ねる（手札 4 枚と 5 枚、終わり方 A と B） | シナリオは 1 つだけ・非公開の意味 | 案（定義の断片）を `--with` で何枚でも重ねる（同じ id は差し替え） |
| U6 | 比べる | 元と案を、同じ条件で多数局回して並べる | selfplay を手で何度も | `bg compare`（元と案の表） |
| U7 | 記録する | どの版・どの案で・何局・どうだったかを残し、改訂の根拠にする | なし | `--record`（試行の記録 experiments.jsonl）と `bg experiments` |
| U8 | 改訂する | 案を本体に取り込み、版を上げ、記録・日誌に理由を書く。古い対局は rebase | diff・rebase | スキル bg-iterate（改訂の 1 周の手順） |
| U9 | 人と遊ぶ | 仲間に渡す手引き（ルールブック）を作り、画面か TTS で遊ぶ | serve・tts | `bg rulebook`（手引きのルールと部品の一覧。詳細ルールは出さない） |
| U10 | エージェントと遊ぶ | 席ごとの見え方だけで遊ばせ、詰まり・穴を拾う | bg-playtest | （変えない） |

## 判断（推奨で決めた。RUL-018）

| # | 問い | 決めたこと | 理由 |
|---|---|---|---|
| V1 | 案をどう持つか | 定義と同じ形式の断片（YAML）を、対局・回すときに重ねる（`--with`、何枚でも、順に）。並びの要素は id が同じなら差し替え、無ければ足す。辞書は中まで重ねる | 形式を膨らませない（RUL-016 の 6）。案ごとに定義を写すと、本体の直しが案に伝わらない |
| V2 | シナリオとの違い | シナリオは対局ごとの非公開の設定（脚本）。案は公開の設計の違い。両方とも重ねる仕組みは同じで、順は 案 → シナリオ | 意味が違うので名前を分ける |
| V3 | 試行の記録の置き場 | ゲームの作業場の `experiments.jsonl`（1 行 1 試行）。版・定義の指紋・案・人数・局数・結果・日時 | git で差が読め、追記だけで壊れにくい |
| V4 | 比べ方 | 元と案を、同じ種（seed）・同じ局数で selfplay し、終わり方の割合・平均の手番数・決着なしの割合を表にする | 作品を問わず回せる物差し。強い手の比較は bg-balance（作品のボット） |
| V5 | 設計の状態 | `bg status`：版、ルール（手引き・詳細）、文だけのルール、未決の裁定、open_questions、複雑さの数、最近の試行 | 「何が決まっていないか」を 1 か所で見る |
| V6 | 手引き | `bg rulebook`：概要、人数、部品（種類と数）、準備・手番・終わりのルール（詳細ルールは出さない）、用語、決まった裁定 | 人の試し遊びには、定義の YAML ではなく読み物が要る |
| V7 | スキル | bg-start（導入〜作業場〜最初の 1 局）と bg-iterate（状態を見る → 案を作る → 比べる → 記録 → 取り込む）。既存の bg-design・bg-playtest・bg-balance へつなぐ | 入口と改訂の 1 周に、手順の決まった案内が要る |
| V8 | 形式 | CTR-F-001 は変えない。作業場・案の重ね方・試行の記録は新しい契約 CTR-F-007 | 定義の形式とは別の、作業の置き方の取り決め |

## 実装と確かめ（2026-11-21）

- SPC-071〜077 を実装し、受入基準を tests/test_v2.py（AC-071-1〜AC-077-1）で確かめた。
- プラグインのフォルダの外（別のプロジェクト）から bin/bg で、init → check → compare --record → status → rulebook が動くことを確かめた。
- 使ってみて足したもの：selfplay の席ごとの勝ちの割合（win_rate。改訂で一番見たい「先手が強すぎないか」）。
- 使ってみて直した不具合：selfplay が、時機つきの終わり（その巡を終えてから）で、結果が記録される前に打ち切っていた（auto_end の定義では結果まで進める）。
- 今回しないこと（次の候補）：案どうしの差が偶然かどうかの目安（信頼区間）、印刷用のカードの版下、案を本体に取り込むコマンド（今はスキルの手順で手で移す）、人の試し遊びの記録（手で書く感想）を試行の記録に足すこと。
